spring-rag System Map

A console RAG chat demo: five containers, one document, and two paths through the stack — a one-time ingestion at startup, and a retrieval round trip on every question typed at the prompt. Both are traced, one trace per turn.

ingestion (once, at startup) retrieval (every turn) tracing (out of band)

Deployment: who talks to whom

Everything runs as Compose services on one bridge network. The app holds the terminal (stdin_open, tty) and is the only component that initiates traffic — Qdrant and Ollama never call back into it.

One turn at the prompt

Each line you type runs the full advisor chain. Two advisors are stacked as builder customizers: chat memory replays the window of prior turns, and the question-answer advisor performs the retrieval and splices the chunks into the prompt. Both round trips to Ollama — the embedding and the completion — happen inside a single call().

That same turn is also one trace. SpringRagApplication opens a chatloop.turn observation around the call(), which does two things: it times exactly the wait between enter and answer, and — because an open observation is in scope — it adopts Spring AI’s own spans as children. Without it, each of the four steps above would arrive in Tempo as its own unrelated root trace.

The nesting is the surprise. Fig. 2 draws the advisors as a stack, but the trace shows them wrapping one another: retrieval happens inside question_answer and the completion inside call, the terminal advisor that actually talks to the model. Two advisors are configured in ChatClientConfig; four appear here, because Spring AI inserts its own tool-calling and terminal advisors into the chain. The durations below are from a real turn, and they show where the argument about model choice actually lives: retrieval cost 78ms, generation cost 56.4 of the 56.6 seconds.

chatloop.turn                  56,598ms — turn.question, turn.answer, conversation.id
└─ spring_ai chat_client
   └─ message_chat_memory         MessageChatMemoryAdvisor
      └─ tool _calling            Tool Calling Advisor

            ├─ qdrant query       78ms — 2 search, 3 chunks

            │     └─ http post

                  └─ http post

What the trace does not carry is the text: the assembled prompt, the completion, and the chunks Qdrant actually returned all go to the console instead, because Spring AI’s content observations write to a logger rather than onto spans. Each of those log lines carries the turn’s traceId, which is what joins the two halves. The reasoning, and the deferred Loki option that would close the gap, are in ADR 0002.

Startup ingestion, and the guard that skips it

Ingestion is an ApplicationRunner at @Order(0), so it completes before the REPL opens. It begins by probing the store with the document URL as the query text — a hit means something has already been ingested, and the whole pipeline is bypassed.

The three source files

SpringRagApplication

src/main/java/uk/bit1/springrag/

Boot entry point plus the console REPL. Reads lines until EOF (Ctrl+D), skips blank input, and tags every call with the fixed conversation id DEMO so one session shares one memory window.

RagIngestionConfig

src/main/java/uk/bit1/springrag/

The startup ingestion runner of Fig. 3 — probe, read, split, store. The only component that writes to the vector store.

ChatClientConfig

src/main/java/uk/bit1/springrag/

Holds the answering guidance in a system prompt, and registers the two advisors. The prompt is where the behavioural rules live: ask before judging, never invent a delivery date or verdict, and always disclose manual review for watch-listed customers.
