# spring-rag

A minimal command-line RAG (retrieval-augmented generation) chat demo built with Spring AI.

On startup, it ingests a document into a vector store, then opens an interactive
console prompt where you can ask questions. Answers are generated by a local LLM
(via Ollama), augmented with relevant chunks retrieved from the ingested document.

## How it works

- **Ingestion** (`RagIngestionConfig`): reads the document at `rag.document.url`
  using Apache Tika, splits it into token-sized chunks, and stores the embeddings
  in Qdrant. If the vector store already has data, ingestion is skipped.
- **Chat** (`ChatClientConfig`, `SpringRagApplication`): a `ChatClient` is configured
  with a sliding-window chat memory (last 500 messages) and a `QuestionAnswerAdvisor`
  that retrieves relevant chunks from Qdrant and injects them into the prompt. The
  app then runs a REPL loop in the console, reading your input and printing the
  model's response.
- **Models**: chat completions use `llama3.1:8b` and embeddings use `nomic-embed-text`,
  both served by a local Ollama instance. Models are pulled automatically on first
  run if missing.

## Prerequisites

- Docker and Docker Compose

Everything — the app itself, Qdrant, and Ollama — runs as containers defined in
`compose.yaml`. No local Java or Gradle install is required.

## Running

The app is interactive (it reads questions from stdin), so start its dependencies
in the background first, then run the app attached to your terminal:

```bash
docker compose up -d qdrant ollama
docker compose run --rm app
```

The first `docker compose run` will build the app image (see `Dockerfile`) and may
take a minute. On first run, Ollama will also pull `llama3.1:8b` (~4.9GB) and
`nomic-embed-text`, which can take a few minutes depending on your connection. Once
ready, you'll see:

```
How can I help?

>
```

Type a question and press Enter.

**Expect to wait.** Ollama runs `llama3.1:8b` on the CPU here, with no GPU offload,
so a single answer takes a few minutes on a typical laptop — long enough to look
like a hang when it is not. If you would rather have fast answers than accurate
ones, set `spring.ai.ollama.chat.model=llama3.2:3b`: it responds in seconds, at the
cost of inventing refund verdicts when it has no facts to base them on (see
`docs/probe-questions.md`). Use Ctrl+D to exit the app container (`qdrant`
and `ollama` keep running — stop them with `docker compose down` when you're done).

If you change the source code, rebuild the image with:

```bash
docker compose build app
```

## Using your own document

By default, the app ingests `src/main/resources/refunds.md`. To use a
different document, drop it into the `documents/` folder (mounted into the app
container at `/documents`) and point `rag.document.url` in
`src/main/resources/application.properties` at it:

```properties
rag.document.url=file:///documents/mydoc.pdf
```

Then rebuild the image so the new property is picked up:

```bash
docker compose build app
```

Tika supports many formats (PDF, Word, HTML, plain text, etc.).

**Note:** ingestion only runs if the vector store is empty, so pointing
`rag.document.url` at a new document is not enough on its own — the startup check
finds the previous document's vectors and skips. Discard them by removing the
`qdrant` container, which holds no volume:

```bash
docker compose rm -sf qdrant
```

Avoid `docker compose down -v` for this: it would delete the `ollama-data` volume
too, throwing away the cached models and forcing a ~4.9GB re-download on the next
run.

## Configuration

Key settings live in `src/main/resources/application.properties`:

| Property | Purpose |
|---|---|
| `rag.document.url` | Source document to ingest |
| `spring.ai.ollama.chat.model` | Chat model (default `llama3.1:8b`) |
| `spring.ai.ollama.embedding.model` | Embedding model (default `nomic-embed-text`) |
| `spring.ai.vectorstore.qdrant.initialize-schema` | Auto-creates the Qdrant collection |
| `management.opentelemetry.tracing.export.otlp.endpoint` | Where traces go (see [Viewing traces](#viewing-traces)) |
| `spring.ai.chat.observations.log-prompt` | Logs the prompt as sent to Ollama, chunks included |

`compose.yaml` overrides a few of these at runtime so the `app` container can
reach its dependencies by service name instead of `localhost`:
`SPRING_AI_OLLAMA_BASE_URL`, `SPRING_AI_VECTORSTORE_QDRANT_HOST`,
`SPRING_AI_VECTORSTORE_QDRANT_PORT`, and
`MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_ENDPOINT`. It also sets `SPRING_DOCKER_COMPOSE_ENABLED=false`
since the app is already being orchestrated by Compose, rather than starting
its own nested Compose stack.

## Viewing traces

Every turn is traced. Grafana and Tempo start with Qdrant and Ollama - there is no flag to
remember - so once the app is running, open:

```
http://localhost:3000
```

Then **Explore** -> the **Tempo** datasource -> **Search**, with service name `chatloop`. No
login: anonymous access is on.

Each turn is one trace, named `chatloop.turn`, lasting exactly as long as you waited for the
answer. Opening one shows where that time went:

```
chatloop.turn                     <- your question and the answer, as span attributes
└─ spring_ai chat_client
   └─ message_chat_memory         <- the advisor chain nests, it does not fan out
      └─ tool _calling
         └─ question_answer
            ├─ qdrant query       <- topK = 4, similarity >= 0.5
            │  └─ embedding       <- the question becoming a vector
            │     └─ http post
            └─ call
               └─ chat llama3.2:3b
                  └─ http post
```

The shape is the point: each advisor wraps the next rather than sitting beside it, so the
retrieval work appears *inside* `question_answer` and the completion *inside* `call`, the
terminal advisor. The `http post` leaves are the actual Ollama round trips.

It also settles an argument about where the time goes. In a measured 56.6s turn, the Qdrant
query took 78ms and the embedding 71ms of that; `chat llama3.2:3b` took 56.4s. Retrieval is
free and generation is everything - which is why the model choice is commented the way it is in
`application.properties`.

Startup ingestion is its own trace, `chatloop.ingest`. On a run that skips ingestion because
Qdrant already holds data, it is nearly empty - which is the answer to "did it re-ingest?".

To follow one session, the app prints a short session id at startup:

```
Session 3f8a1c04 - search Grafana for this id to find this session's traces.
```

Search on `conversation.id` to get just that session's turns.

### Finding the prompt and the retrieved chunks

These are **not** in Tempo - they are in the app's own console output, because Spring AI's
content observations write to a logger rather than onto spans. Each log line carries the
`traceId` of the turn it belongs to, so the two line up:

- the prompt as actually sent to Ollama, with the system prompt, the chat memory and the
  retrieved policy chunks spliced in
- the completion that came back
- the documents Qdrant returned for the query

That split, and why it was accepted rather than worked around, is recorded in
[ADR 0002](docs/adr/0002-tracing-always-on-content-in-logs.md). It is also why these settings
are fine here and would not be in a real system: in production that console is full of customer
data.
